# GOODLIFE Radio — Compliance Audit (Code Only, Read-Only)

**Date:** 13 November 2026
**Scope:** the GOODLIFE radio module inside `goodlife-event-tickets`, plus the `scripts/` and `home-server/` pieces that feed it.
**Prepared by:** an engineer, not a lawyer. This report describes what the code does and which rule it *may* touch. It is **not legal advice** and contains **no legal conclusions**. Every point that depends on how the law applies is marked **Needs legal confirmation**.
**Read-only statement:** no application code was changed, nothing was deleted, no migrations or scripts were run, and **no query was made against any live or production database**. This file is the only new artefact. No secret values, keys, passwords, tokens or phone numbers from the code are printed; they are referred to by variable or field name only.
**Method:** nine parallel read-only code audits, each checked against the actual files; then re-checks of the highest-risk claims by the author. Documents were read first (`docs/ARCHITECTURE.md`, `docs/RADIO-PLAN.md`, `docs/BUILD-SPEC.md`, `docs/PHASE-1` to `PHASE-5-REPORT.md`). **Where the documents and the code disagree, this report uses the code.**

**Status labels used throughout:** `Compliant by design` (a technical control exists — this is an engineering observation, not a legal one) / `Partly addressed` / `Not addressed` / `Needs legal confirmation`.

**Important document-vs-code note.** `docs/ARCHITECTURE.md` is an earlier review (12 November 2026) and says the station has **no presenter accounts, no timetable, no show slots, no contests and no tips**. The code now contains all of these (`migrations/radio/20261115_01` to `_04`, `app/presenter/*`, `app/radio/schedule`, `app/radio/apply`, `app/api/radio/contests/*`, `app/api/radio/tips/*`, `app/api/radio/shoutouts/*`). That must be confirmed before relying on any record.

## 1. Executive summary (under 250 words)

The radio module is a working internet station with 24/7 playout, live DJs, AI drops, a replay vault, shoutouts, polls, giveaways, tips, sponsors, a timetable and presenter accounts. It has **no music-rights layer**. Music mainly arrives through a Python bridge that downloads YouTube/SoundCloud audio with `yt-dlp`/Invidious into a **public R2 bucket**. The catalogue table (`radio_sets`) has no ISRC, rights holder, licence, territory, source URL or "cleared for broadcast" field, and nothing checks rights before a track is aired. The vault has an explicit **"Download Master MP3"** link; the public API returns the raw storage key; recordings marked private are hidden from listings, not from the file. No music usage report or per-period revenue figure is possible.

**Top risks:** (1) third-party music ingest with no rights records; (2) public downloadable full sets and 320 kbps masters; (3) AI voice drops with no listener disclosure, no mandatory review and no voice-consent record; (4) giveaways with no rules/cost/prize text and an unimplemented random draw; (5) names, phones and WhatsApp message bodies stored with no consent notice or deletion jobs; (6) no explicit flag, watershed filter, ad labelling or ad-minute cap; (7) no complaints procedure, editorial policy or record that presenters saw the Programming Code.

**What is already good:** per-presenter stream keys with logged attempts; shows and slots; fail-closed secrets; recordings private in the database; shoutout phones omitted publicly and masked for presenters; reminders dry-run by default with STOP opt-out; pseudonymous polls; partial AI fact checks; coarsened, short-lived location data. Building blocks only.

## 3. Findings by area

### 3.1 Music sourcing and library — **Not addressed** (licence/tariff questions: **Needs legal confirmation**)

**What the code does.** A Python "ingestion bridge" (`scripts/radio-bridge-server.py`) searches Invidious, falls back to `yt-dlp` (`search_ytdlp`, `extract_playlist_ytdlp`), builds a `youtube.com/watch?v=…` URL in `process_single_track()`, extracts the audio stream with `yt-dlp -f ba/b`, normalises it with ffmpeg, uploads a 160 kbps MP3 plus the YouTube thumbnail to Cloudflare R2, and posts the result to `app/api/webhooks/radio-ingest/route.ts`. A second path (`home-server/daemon/services/audio_fetcher.py`, used by `home-server/daemon/main.py::queue_next_url`) imports `yt_dlp` for "YouTube, SoundCloud, or direct URLs", extracts 320 kbps MP3 and uploads straight into AzuraCast without creating a catalogue row. `app/api/admin/radio/search/route.ts::searchYouTubeFallback()` scrapes YouTube search results; `lib/radio/playlist-resolver.ts` scrapes YouTube playlists and Spotify embeds. Tracks also enter by admin upload (`app/api/admin/radio/multipart/route.ts`, `register-upload/route.ts`), batch ingest (`app/api/admin/radio/batch-ingest/route.ts`, which can store a raw YouTube page URL as `audio_url`) and quick insert (`components/admin/radio/LibraryIngestDock.tsx` → `app/api/admin/radio/queue-next/route.ts`). Lyrics are fetched from `lrclib.net` (`lib/radio/lyrics-service.ts::fetchTrackLyrics`) and served publicly by `app/api/radio/playout-state/route.ts`.

**Rules it may touch.** 5.5.1.2/5.5.1.3/5.5.1.4 (royalties, contracts with licensing bodies before broadcast, written proof to CA), 5.4.2(b) (guard against copyright/trademark infringement in UGC), the KECOBO tariff, and the unresolved KICA s46C licence question.

**Evidence.** `radio_sets` columns observed in `lib/radio/types.ts::RadioSet` and the INSERT statements are: `id, event_id, title, dj_name, audio_url, audio_high_url, r2_key, r2_high_key, cover_url, duration, duration_sec, genre, file_size, file_size_high, bitrate, bitrate_high, source_type, external_id, processing_status, error_message, display_order, is_active, play_count, bpm, musical_key, energy, is_full_set, key_source, key_confidence, bpm_confidence, analysis_method, analysis_version, analyzed_at, created_at, deleted_at`. `source_type` records storage/origin only (`'r2'`, `'youtube'`, `'spotify'`); `external_id` is a platform video/track id; `dj_name` is the channel/artist label, not a rights holder. **Not found:** ISRC, artist column, rights holder, licence, licence expiry, territory, source URL, copyright/royalty field, explicit flag, or "licensed for broadcast" gate — searched `lib/radio/`, `app/api/admin/radio/`, `app/api/webhooks/radio-ingest/`, `migrations/`, `home-server/daemon/`, `scripts/`. `radio_sets` has no create-table migration in the tracked repository. No gate exists before a track enters rotation: only `is_active`, `deleted_at IS NULL`, `processing_status='ready'` and a non-empty playlist are checked (`app/api/admin/radio/playlists/[id]/activate/route.ts`, `lib/radio/playlist-slotter.ts`, `lib/radio/sequencer.ts`, `lib/radio/broadcast-state.ts`).

**Fix needed.** Per-track rights/source fields (ISRC, rights holder, licence reference, licence expiry, territory, source URL, explicit flag, clearance flag); a "licensed for broadcast" gate on insert, playlist add, playlist activation and playout; a place to store contracts/proof; the ingest pipeline should not be able to add a track to rotation without clearance. Whether an artist's direct permission is sufficient is a question for a lawyer/KECOBO (section 8, Q8).

**Doc-vs-code.** `docs/ARCHITECTURE.md` §16.4 flags this risk and is corroborated. `docs/PHASE-3-REPORT.md:119` mentions `is_cleared_for_broadcast = true` — **not found anywhere in code or migrations**; that section is a design note, not a feature. `docs/PHASE-1-REPORT.md` column lists do not match `migrations/radio/20261115_01_radio_schedule_tables.sql`.

### 3.2 Playback, replays and downloads — **Not addressed**

**What the code does.** `components/radio/FestivalSetVault.tsx` renders, for each public recording, an explicit `<a href={rec.audio_url} download … title="Download Master MP3">` link and advertises "320kbps Master" recordings. `app/api/radio/recordings/route.ts` is a **public, unauthenticated GET** that returns both `audio_url` **and the raw `r2_key`** in JSON for rows `WHERE r.is_public = true`. `app/radio/shows/[slug]/page.tsx` renders a native `<audio controls src=…>` (which also permits saving). `app/api/radio/state/route.ts`, `app/api/radio/live/route.ts` and `app/api/radio/playlists/[id]/route.ts` hand `audio_url` and `audio_high_url` to any browser. `context/RadioContext.tsx` (`playSet`, `playCurrentTrackAudio`, `startBackupMix`) sets `audio.src` to those URLs with no token. In virtual mode the listener's browser downloads the **whole MP3** and seeks to a computed offset. `lib/radio/r2-signer.ts` uses `PutObjectCommand` only; every helper builds `publicUrl = ${R2_PUBLIC_DOMAIN}/${key}`. There is **no `GetObjectCommand`, no signed or short-TTL playback URL**. `home-server/daemon/services/archiver.py::upload_to_r2` uploads 320 kbps masters to predictable keys and returns a public URL. `lib/radio/audio-prober.ts::probeAudioMetadata` fetches byte ranges from any `audio_url`, confirming unauthenticated reads.

**Rules it may touch.** 5.5.1.1–5.5.1.4 (obligations for the rights exploited; written proof), the KECOBO category question — a downloadable, on-demand vault may be viewed differently from a linear broadcast — 5.3 (no local-content evidence), and the unresolved KICA s46C licence question.

**Evidence.** `radio_recordings.is_public` is added in `migrations/radio/20261115_02_phase2_live_handover.sql` with `approved_by_id`, `approved_at`, `slot_id`, `show_id`, `presenter_id`. Approval endpoints: `app/api/admin/radio/recordings/[id]/approve/route.ts`, `app/api/presenter/recordings/[id]/approve/route.ts`. **The flag only hides the database row / UI listing — it does not protect the file.** The R2 object was uploaded to a public URL before the row existed, and the public API returns the key. **Not found:** `stream_only`/`downloadable`/`allow_download` flags, `Content-Disposition` on audio, hotlink/referrer rules, obfuscated keys, private bucket, or any playback token — looked in `components/radio/`, `app/api/`, `lib/radio/r2-signer.ts`, `lib/r2-storage.ts`, `next.config.ts`, `middleware.ts`, `migrations/`. `audio_high_url`/`r2_high_key`/`bitrate_high`/`is_full_set` are metadata only; `lib/radio/bitrate.ts` switches live stream mount names, not R2 files.

**Fix needed.** Private bucket plus server-issued short-TTL signed playback URLs; enforce `is_public` at the storage layer; remove or gate the `download` link and native controls; stop returning `r2_key`/`audio_high_url` in public JSON; add an explicit stream-only vs downloadable distinction; add rights/territory fields.

**Doc-vs-code.** `docs/ARCHITECTURE.md` §9.3 says a listener "cannot download a live set unless it has already been archived and made public" — **contradicted** by the download anchor and by `is_public` not gating R2. §14 finding #9 ("R2 objects are public and directly hotlinkable") **matches** the code. `docs/PHASE-2-REPORT.md` says private-by-default with approval — true for the database flag, but it presents approval as controlling availability; the code shows it does not. `docs/PHASE-2-REPORT.md` describes `/api/radio/live` as an audio redirect; the code returns JSON with `now_playing.audio_url`.

### 3.3 Play logs and reporting — **Not addressed**

**What the code does.** `app/api/radio/play-event/route.ts` is the only writer of `radio_plays`. A browser beacon (`context/RadioContext.tsx` → `navigator.sendBeacon`) records **how long a listener's browser was tuned in**; in live mode it snapshots the upstream `${RADIO_UPSTREAM_URL}/api/now-playing` title/artist. In vault mode it increments `radio_sets.play_count`. `app/api/radio/heartbeat/route.ts` + `lib/radio/listener-tracker.ts` maintain `radio_listener_pings`. Now-playing is **computed from clock arithmetic** — `(now − radio_playlists.activated_at) % Σ duration_sec` — in three separate code paths (`app/api/radio/state/route.ts`, `app/api/radio/live/route.ts`, `lib/radio/broadcast-state.ts`), and **nothing is written to a log**. In autodj mode `app/api/radio/live/route.ts` returns `history: []`. The home-server Liquidsoap (`home-server/liquidsoap/goodlife-station.liq`) records audio to disk but writes no play metadata to the database; `home-server/daemon/main.py` only proxies AzuraCast now-playing. The external upstream `/api/history` is not in this repo and is passed to browsers without being stored. The only CSV export is tips (`app/api/admin/radio/tips/route.ts?format=csv`); `components/admin/radio/RadioTelemetryLogs.tsx` shows a "Total Plays" count, not a track list.

**Rules it may touch.** 5.5.1.4 (written proof / contracts shown to CA), KECOBO royalty calculation and returns, 14.5 (records retained one year), and general regulator record-keeping.

**Evidence.** `radio_plays` columns: `id, set_id, session_hash, seconds_listened, completed, quality_used, created_at` (`scripts/migrate-radio-v3.js`) plus `mode, track_title, track_artist` (`migrations/20261028_make_radio_plays_set_id_nullable.sql`). No ISRC, no track-id, no play timestamp per track, no duration, no show, no presenter. `radio_drops.played_at`/`play_count` are read but never written. Retention: `radio_listener_pings` purged after 10 minutes; `cleanupExpiredRadioDrops(168)` deletes drops older than 7 days; **no** `DELETE FROM radio_plays` and no retention on connection/audit/recording/slot tables. `radio_connection_log`, `radio_audit_logs`, `show_slots` and `radio_recordings` do carry timestamps and presenter links, but none of them say which **track** aired.

**Fix needed.** A server-side, authoritative airplay log written by the actual playout engine at each track start, with `played_at`, `track_id`, `track_title`, `artist`, `isrc`, `label/album`, `duration_sec`, `show_id`, `slot_id`, `presenter_id`, `playout_source` (R2 / Liquidsoap / AzuraCast), `play_type` (music / jingle / ad), `licence_ref`; a retention policy of at least one year; an authenticated CSV export; reconciliation of the two playout systems.

**Doc-vs-code.** `docs/ARCHITECTURE.md` §8.2 says `/api/radio/live` returns recent `history` — code returns an empty array in autodj mode, and live history is an unpersisted upstream proxy. §5.1 omits `listener_city`, which `lib/radio/telemetry.ts` queries. §16.1 ("no migration runner") is now outdated: `migrations/radio/20261115_01`–`_04` create the schedule, connection-log, interaction, tips, sponsors and audit tables. `docs/PHASE-5-REPORT.md` claims audit logging of actor/role/action/time — an INSERT exists in `lib/radio/ops-service.ts`, but there is no query/export surface and no retention.

### 3.4 Revenue records — **Partly addressed**; a KECOBO-ready net-revenue figure: **Not addressed**

**What the code does.** Listener tips are the only radio money recorded. `app/api/radio/tips/initialize/route.ts` creates a `TIP-XXXX` reference, checks the PayHero service wallet, calls `lib/radio/ops-service.ts::createRadioTip` and starts an STK push. `app/api/payhero/callback/route.ts` routes `TIP-` references to `fulfillRadioTip` so tips never mint tickets. `radio_tips` (`migrations/radio/20261115_04_phase5_ops_money.sql`) stores `id, reference, amount, phone, phone_hash, sender_name, message, slot_id, presenter_id, status, payhero_reference, mpesa_receipt, created_at, completed_at`. `amount` is the **gross** requested tip; there is no fee or net column. `app/api/admin/radio/tips/route.ts` offers `format=csv` (columns: ID, Reference, Status, Amount, Sender Name, Presenter, Show, Created At, Receipt) capped at 1000 rows, mixing pending/failed with completed, with **no date filter and no total row**; JSON gives an all-time `SUM` of completed amounts. `app/api/admin/radio/analytics/route.ts` gives an all-time `total_tipped_kes`. Neither endpoint is called by any UI component.

Sponsors: `radio_sponsors` has `name, logo_url, link_url, tagline, show_id, slot_id, is_active, starts_at, ends_at` — **no amount, contract value, invoice or revenue field**. `components/radio/SponsorBanner.tsx` shows "BROUGHT TO YOU BY" with only `target`/`rel` (no click tracking), mounted only on `app/radio/schedule/page.tsx`. Ads/drops (`lib/radio/drop-engine.ts`, `lib/radio/cron-engine.ts`, `components/admin/radio/DropStudio.tsx`) have no advertiser, no charge and no ad-minute counter. Ticket-linked promotion (`components/radio/UpcomingEventCard.tsx`, `lib/radio/events.ts`) is a plain `/?event=` link with no radio attribution. Settlements/budget APIs are event/vendor scoped; there is no per-period "radio revenue" figure anywhere.

**Rules it may touch.** KECOBO tariff (definition of "net revenue", the 4% or flat 250,000 KSh category, 1-year licence, 5% compounded monthly late penalty — **all unverified**), 11.2.12 (ad-minute cap needs an ad log), 12.4.2.3 (cost disclosure), and tax on tips/sponsor income (**unresearched**).

**Fix needed.** `from`/`to` filters on tips; a total aligned with the CSV; gross vs net (PayHero fee) per tip; money/invoice fields on `radio_sponsors`; an ad log (advertiser, aired-at, charge, ad minutes per half hour); a radio attribution tag for ticket sales; wire the CSV/total into an admin UI; confirm the Phase-5 migrations were applied to production before relying on any records.

**Doc-vs-code.** `docs/BUILD-SPEC.md` decision 11 (tips are GOODLIFE revenue, presenters paid via staff module) is consistent with code. `docs/PHASE-5-REPORT.md` claims `radio_presenters` and `scripts/phase5-migrations.sql` — **not found**; the real table is `presenters` and the file is `migrations/radio/20261115_04_phase5_ops_money.sql`. It claims sponsor banners on schedule **and** show pages plus "tracking attributes" — the banner is only on the schedule page and has no tracking attributes. It claims tips are "available in admin console" — the endpoints exist but no client calls them. It also says migrations were dry-run only, not applied to production.

### 3.7 Contests and giveaways — disclosure **Not addressed**; fairness **Partly addressed**; BCLB position **Needs legal confirmation**

**What the code does.** `app/api/radio/contests/route.ts` `POST` (presenter or admin) creates a contest with `title, description, passphrase, contest_type` (DB allows `passphrase|random_draw|trivia`), `event_id, tier_id, max_winners` (clamped 1–5), `duration_minutes`, `slot_id`. `GET` returns `id, slot_id, title, description, contest_type, status, event_id, tier_id, max_winners, winners_awarded, starts_at, ends_at, event_title, dj_name` — the passphrase and listener data are omitted. `components/presenter/PresenterInteractionTools.tsx` hardcodes `contest_type: "passphrase"` and never sends `description`.

**Winner selection — read carefully.** `app/api/radio/contests/enter/route.ts` is a **first-correct-answer race**, not a random draw and not skill judging: for `passphrase`, `cleanAnswer === contest.passphrase.toLowerCase()` sets `isWinner = true`. There is no knowledge test — it is equality against a shared secret spoken on air. For `random_draw` and `trivia`, the `else` branch only inserts an entry with `is_winner = FALSE` and replies "The winner will be picked live on air"; **there is no draw, no judging, no finalise endpoint anywhere**. So those types never award a ticket in code, and any real "live draw" would be an off-code, chance-based process. Winners get a genuine free ticket (`createTicket` with `amount_paid: 0`, `ticket_type: "<tier> (Radio Winner)"`) and a WhatsApp pass.

**Concurrency:** the `SELECT` has **no `FOR UPDATE`** and there is no transaction; the cap is a separate read (`winners_awarded >= max_winners`), the ticket is minted **before** `UPDATE radio_contests SET winners_awarded = winners_awarded + 1 …` and that UPDATE has no `WHERE winners_awarded < max_winners` guard. Only the DB constraint `chk_contest_winners_cap` backstops it, so two simultaneous winners could both pass the read. A schema mismatch also exists: `radio_contest_entries.awarded_ticket_id` is declared `INTEGER REFERENCES tickets(id)` while `tickets.id` is `TEXT` and the code passes a `WIN-…` string — the winning-entry INSERT is likely to fail.

**Rules/costs/prize display:** `components/radio/LiveContestWidget.tsx` shows a "ON-AIR FESTIVAL PASS GIVEAWAY" label, the title, an optional description, "{N} PASS(ES) LEFT" and a name/phone/answer form. `ends_at` and `event_title` are returned but **never rendered**. **Not found:** rules, eligibility, "free to enter"/cost, closing time, prize description or value, winner-selection method, terms link, standard SMS/WhatsApp charge, or "no purchase necessary" — searched the widgets, presenter tools, contest routes, `/radio` page and migration.

**Polls:** `app/api/radio/polls/vote/route.ts` deduplicates on `voter_hash` (phone or IP+User-Agent) with `uq_poll_voter`, 409 on duplicates, 20/min rate limit — but no login, no change-vote path, and `app/api/radio/polls/route.ts` computes `voterHash` from the IP only, which generally **will not match** the stored hash, so `has_voted` / results may never display. Voting is not tied to a prize; the widget says the winning track is "suggested directly to the DJ's live decks" with no advisory-only disclosure.

**Rules it may touch.** 12.4.2.1–.5 (fair voting, not misleading, rules and cost fully disclosed, prizes accurately described), 12.4.1 / 12.3.2 (whether a giveaway is a "gambling activity" needing BCLB authorisation), 11 (gambling ads), 7.3.8 (name/phone collected with no visible notice), and Kenya's lottery/prize-competition law (**unresearched**).

**Fix needed.** Structured rules/cost/prize/closing-time/winner-method fields plus UI text; atomic cap (`FOR UPDATE` + guarded UPDATE inside a transaction) — note the Phase-4 "atomic" claim is overstated; decide whether `random_draw` is in scope at all and, if so, build and log it; fix the `awarded_ticket_id` type; align poll hashing; disclose that voting is advisory; add notice/consent for name+phone.

**Doc-vs-code.** `docs/PHASE-4-REPORT.md`: "atomic festival ticket issuance" — **contradicted**; "passphrase and trivia" — only passphrase works; "max winners cap strictly enforced" — true on the single path, racy under concurrency; `awarded_ticket_id VARCHAR(50)` — three-way mismatch (doc / migration `INTEGER` / actual `tickets.id TEXT`); `scripts/phase4-migrations.sql` — **not found**.

### 7.1 If there is genuinely no budget

The owner has said there is no cash for fees. These cost little or nothing and reduce exposure while Q2/Q13 are with KECOBO. They are operational choices, **not** a legal position — every one still needs legal confirmation.

1. **Stop the money and the copying.** Turn off tips, sponsors and contests (the tariff is reported as a percentage of net revenue); disable the `yt-dlp`/Invidious ingest; remove public downloads and the public vault. Files: `scripts/radio-bridge-server.py`, `components/radio/FestivalSetVault.tsx`, `app/api/radio/recordings/route.ts`, `app/api/radio/tips/*`, `app/api/radio/sponsors/route.ts`. Zero cost, reversible, and it removes the two highest-ranked risks in section 4.
2. **Play only audio you control.** Own jingles, spoken word, interviews, and live sets from DJs who own every right, with permission **in writing** (5.5.1.3/5.5.1.4 expect contracts and proof). Freely licensed or public-domain tracks are usable only where the licence explicitly permits broadcasting **and** on-demand replay — "royalty-free" does not mean "no rights", and a CMO may still collect.
3. **Ask in writing before assuming.** The two draft emails in section 9 (Q13 added) cost nothing to send. A written answer on the correct category, zero-revenue treatment, per-event licensing and staged payment is more reliable than guessing from news reports.
4. **Launch as talk; add music later.** A station with no third-party music and no revenue is a different starting point from a 24/7 music station with a downloadable master vault. Whether that changes the tariff at all is **Needs legal confirmation**.

**Why a "just don't pay" approach is a poor fit here:** the code makes this station highly identifiable — a named Kenyan domain, M-Pesa/PayHero payments, sponsors, a public presenter timetable, named shows, and a live listener map. The regulator's own reported position (The Standard, "KECOBO clarifies livestreaming directive…") is that a DJ who live-streams recorded music "has become a radio station" and needs licences. Nothing in the code creates an exemption.
